# Logging

The rotation Lambda writes one JSON record per event to its CloudWatch Logs
log group (`JwksSecret.rotationLogGroup`), in the
[Elastic Common Schema](https://www.elastic.co/docs/reference/ecs) (ECS) 8.11.
This page describes what is logged and how to consume it: the
[schema](#logging-schema), the [event reference](#event-reference), how to
[query and alert on the logs](#consuming-the-logs) and, for auditors, the
[OWASP Logging Cheat Sheet control implementation](#owasp-logging-cheat-sheet-control-implementation).

The records are the function's own account of what it decided: which keys a
rotation added and retired, whether each step passed, and why one failed.
AWS CloudTrail records who called the Secrets Manager APIs, but not those
decisions; see [What CloudTrail already records](#what-cloudtrail-already-records).

## Where the logs go

- **Log group.** The construct creates the log group and grants the rotation
  role write access to it only. It keeps logs for one year
  (`RetentionDays.ONE_YEAR`) and follows the secret's removal policy
  (`RETAIN` by default). Override `retention`, `removalPolicy` and
  `encryptionKey` with `rotationLogGroupProps`.
- **Format.** The construct sets Lambda's Text log format, and the function
  writes each record to `process.stdout` as a single line of JSON. Lambda adds a
  timestamp, request ID and level in front of lines written with `console.log`,
  so the function does not use it. Lambda's JSON log format re-encodes what
  `console` methods write, and its level filtering expects `level` and
  `timestamp` keys, which ECS records do not have, so the construct does not use
  it either.
- **Volume.** A rotation writes at most one event per step, three in all, plus
  one when the function starts (a cold start). A failed step is retried by
  Secrets Manager and logs again on each attempt.

## Logging schema

Every record is a single JSON object with flat, dotted keys (for example
`"event.action"`), following the [ECS logging specification](https://www.elastic.co/docs/reference/ecs/logging/intro).
Fields ECS defines keep their ECS names and types. The project extensions are
listed separately below.

### Fields on every event

| Field               | ECS type          | Presence    | Meaning                                                                                                 |
| ------------------- | ----------------- | ----------- | ------------------------------------------------------------------------------------------------------- |
| `@timestamp`        | `date`            | Every event | When the event was logged, in UTC, as an ISO 8601 string with milliseconds.                             |
| `message`           | `match_only_text` | Every event | Human-readable summary. Query the structured fields instead.                                            |
| `ecs.version`       | `keyword`         | Every event | The ECS version of the record, `8.11.0`.                                                                |
| `log.level`         | `keyword`         | Every event | `info` for a success, `error` for a failure.                                                            |
| `service.name`      | `keyword`         | Conditional | The Lambda function name, from `AWS_LAMBDA_FUNCTION_NAME`.                                              |
| `cloud.provider`    | `keyword`         | Every event | Always `aws`.                                                                                           |
| `cloud.region`      | `keyword`         | Conditional | The function's region, from `AWS_REGION`.                                                               |
| `event.category`    | `keyword[]`       | Every event | `process` for `start_function`, `configuration` otherwise.                                              |
| `event.type`        | `keyword[]`       | Every event | `error` for every failure; otherwise `start`, `change` or `info` as in the [event index](#event-index). |
| `event.action`      | `keyword`         | Every event | The lower-snake-case operation. The outcome is never part of it.                                        |
| `event.outcome`     | `keyword`         | Every event | `success` or `failure`.                                                                                 |
| `aws.xray.trace.id` | `keyword`         | Conditional | The X-Ray trace ID (the `Root` of `_X_AMZN_TRACE_ID`), when Lambda sets one for the invocation.         |

### Fields on rotation events

These are on every event except `start_function`.

| Field              | ECS type  | Presence    | Meaning                                                                                                                 |
| ------------------ | --------- | ----------- | ----------------------------------------------------------------------------------------------------------------------- |
| `event.id`         | `keyword` | Every event | The rotation's `ClientRequestToken`, which is also the new secret version's ID. It joins the events of one rotation.    |
| `event.reason`     | `keyword` | Conditional | A controlled reason, on skipped steps and `validate_rotation` failures. See the [event reference](#event-reference).    |
| `cloud.account.id` | `keyword` | Conditional | The AWS account ID, taken from the secret ARN.                                                                          |
| `error.type`       | `keyword` | Failures    | The error's class name.                                                                                                 |
| `error.message`    | `keyword` | Conditional | The error message, only for errors whose messages are safe to log; see [Sensitive-data policy](#sensitive-data-policy). |

### Project extensions

| Field                                           | Type        | Presence                                        | Meaning                                                                                                                  |
| ----------------------------------------------- | ----------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `aws.secretsmanager.rotation.step`              | `keyword`   | Rotation events                                 | The step Secrets Manager asked for: `createSecret`, `setSecret`, `testSecret` or `finishSecret`.                         |
| `aws.secretsmanager.secret.arn`                 | `keyword`   | Rotation events                                 | The ARN of the secret being rotated.                                                                                     |
| `aws.secretsmanager.secret.version.id`          | `keyword`   | Rotation events                                 | The ID of the version being created and promoted. Equal to `event.id`.                                                   |
| `aws.secretsmanager.secret.previous_version.id` | `keyword`   | `finish_secret`                                 | The version ID that was `AWSCURRENT` before the promotion.                                                               |
| `jwks.kids.current`                             | `keyword[]` | `create_secret`, `test_secret`, `finish_secret` | The `kid`s (RFC 7638 thumbprints) in the pending JWKS, oldest first. After `finish_secret` these are the published keys. |
| `jwks.kids.added`                               | `keyword[]` | `create_secret`, `finish_secret`                | The `kid`s in the pending JWKS that the current JWKS did not have.                                                       |
| `jwks.kids.removed`                             | `keyword[]` | `create_secret`, `finish_secret`                | The `kid`s the current JWKS had that the pending JWKS drops.                                                             |
| `jwks.use`                                      | `keyword`   | `start_function`                                | `sig` or `enc`.                                                                                                          |
| `jwks.alg`                                      | `keyword`   | `start_function`                                | The JWA algorithm of every key.                                                                                          |
| `jwks.key_type`                                 | `keyword`   | `start_function`                                | `EC` or `RSA`.                                                                                                           |
| `jwks.curve`                                    | `keyword`   | `start_function`                                | The EC curve, for EC keys.                                                                                               |
| `jwks.rsa_modulus_length`                       | `long`      | `start_function`                                | The RSA modulus length in bits, for RSA keys.                                                                            |

ECS has no fields for a JWK, so the `jwks.*` fields are project extensions.
The `aws.*` fields follow the ECS convention of putting vendor fields under a
vendor prefix. They are named as follows: an identifier is a nested `.id`
leaf, as in ECS's `trace.id` (`aws.xray.trace.id`), and any other compound
leaf is snake_case, as in ECS's `error.stack_trace` (`jwks.key_type`).

### Sensitive-data policy

- **Key material is never logged.** No JWK member is written to the log, and
  neither is the secret string. The only key data logged is the `kid`, a
  public thumbprint. `test/assets/lambda/handlers/rotation.test.ts` asserts that
  no private member of a generated key appears in the output.
- **Error messages are logged only when they are safe.** `error.message` is
  set for `JwksValidationError`, `JwkOptionsMismatchError` and
  `RotationStateError`, which this package writes, and for Secrets Manager SDK
  exceptions. Any other error, such as one thrown by a cryptography library,
  might echo its input, so only its `error.type` is logged.
- **No stack traces or request payloads.** Stack traces would repeat the
  message of the error. The rotation event is not logged as a whole; only its
  step, secret ARN and token are.
- **Values are data, not markup.** Each record is built with `JSON.stringify`,
  so a value that contains a line break or a quote cannot end the record or add
  a field.
- **The ARN and account ID are logged.** Treat the log group with the same
  access controls as the secret's metadata.

## Event reference

Each event also carries the [fields on every event](#fields-on-every-event).
The tables below list only what is specific to it.

### Function started: `start_function`

Logged once per execution environment, when the handler first runs (a cold
start). Level: `info`. It records the key options the function is configured
with, which are the construct's `algorithm`, `use`, `curve` and
`rsaModulusLength`.

| Field                                   | Presence    | Meaning                     |
| --------------------------------------- | ----------- | --------------------------- |
| `jwks.use`, `jwks.alg`, `jwks.key_type` | Every event | The effective key options.  |
| `jwks.curve`                            | EC keys     | The curve.                  |
| `jwks.rsa_modulus_length`               | RSA keys    | The modulus length in bits. |

### Function failed to start: `start_function`

Logged when the function cannot read its key options, for example because the
`JWK_OPTIONS` environment variable is missing or invalid. Level: `error`. The
error is then thrown, so the invocation fails.

| Field           | Presence    | Meaning                                                                            |
| --------------- | ----------- | ---------------------------------------------------------------------------------- |
| `error.type`    | Every event | The error's class name.                                                            |
| `error.message` | Conditional | Only for the errors listed in the [sensitive-data policy](#sensitive-data-policy). |

### Pending version created: `create_secret`

Logged by the `createSecret` step after it writes the new `AWSPENDING` version.
Level: `info`. It is the record of which keys a rotation adds and retires.

| Field                                         | Presence    | Meaning                                                                                |
| --------------------------------------------- | ----------- | -------------------------------------------------------------------------------------- |
| [Rotation fields](#fields-on-rotation-events) | Every event | The rotation's identity.                                                               |
| `jwks.kids.current`                           | Every event | The `kid`s of the new JWKS.                                                            |
| `jwks.kids.added`                             | Every event | The key added. On the first rotation, both initial keys.                               |
| `jwks.kids.removed`                           | Every event | The key dropped, once the JWKS would otherwise hold more than 3 keys; empty otherwise. |

### Pending version validated: `test_secret`

Logged by the `testSecret` step after the pending JWKS is checked against the key
options and against the current JWKS: it must be exactly the current JWKS
rotated once. Level: `info`.

| Field                                         | Presence    | Meaning                                   |
| --------------------------------------------- | ----------- | ----------------------------------------- |
| [Rotation fields](#fields-on-rotation-events) | Every event | The rotation's identity.                  |
| `jwks.kids.current`                           | Every event | The `kid`s of the validated pending JWKS. |

### Pending version promoted: `finish_secret`

Logged by the `finishSecret` step after the pending version becomes
`AWSCURRENT`. It is the authoritative record that keys are now live, and, in
`jwks.kids.removed`, that keys have been retired. Tokens signed with a retired
key stop verifying once your OpenID Connect server refreshes its cache. Level:
`info`.

| Field                                           | Presence    | Meaning                            |
| ----------------------------------------------- | ----------- | ---------------------------------- |
| [Rotation fields](#fields-on-rotation-events)   | Every event | The rotation's identity.           |
| `jwks.kids.current`                             | Every event | The `kid`s now in the secret.      |
| `jwks.kids.added`                               | Every event | The `kid`s the promotion added.    |
| `jwks.kids.removed`                             | Every event | The `kid`s the promotion removed.  |
| `aws.secretsmanager.secret.previous_version.id` | Conditional | The version that was `AWSCURRENT`. |

### Step skipped: `rotate_secret`

Logged when Secrets Manager repeats a step that has already happened, so the
function changes nothing. Level: `info`.

| Field                                         | Presence    | Meaning                                                                                                                                                                 |
| --------------------------------------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Rotation fields](#fields-on-rotation-events) | Every event | The rotation's identity.                                                                                                                                                |
| `event.reason`                                | Every event | `pending_exists`: the `createSecret` step found its `AWSPENDING` version already created. `already_current`: the token is already `AWSCURRENT`, so any step is skipped. |

### Step failed

Logged when a step throws, just before the error is rethrown, so Secrets
Manager records the failure and retries the step. Level: `error`.
`event.action` is the step's action (`create_secret`, `test_secret` or
`finish_secret`), or `rotate_secret` for a failure that cannot be attributed to
one of them, such as a failed `DescribeSecret` call on the `setSecret` step.

| Field                                         | Presence    | Meaning                                                                                   |
| --------------------------------------------- | ----------- | ----------------------------------------------------------------------------------------- |
| [Rotation fields](#fields-on-rotation-events) | Every event | The rotation's identity.                                                                  |
| `error.type`                                  | Every event | The error's class name, for example `JwkOptionsMismatchError` or `AccessDeniedException`. |
| `error.message`                               | Conditional | Only for the errors listed in the [sensitive-data policy](#sensitive-data-policy).        |

A key option that no longer matches the keys in the secret fails the `createSecret`
step with a `JwkOptionsMismatchError`; see [Changing the key options](how-rotation-works.md#changing-the-key-options).

### Rotation cannot proceed: `validate_rotation`

Logged when the rotation request is inconsistent with the secret's state, before
any step runs. The error is then thrown. Level: `error`.

| Field                                         | Presence    | Meaning                                                                                                                                                                                                                                                   |
| --------------------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Rotation fields](#fields-on-rotation-events) | Every event | The rotation's identity.                                                                                                                                                                                                                                  |
| `event.reason`                                | Every event | `rotation_disabled`: rotation is not enabled on the secret. `version_not_found`: the token has no stage on the secret. `version_not_pending`: the token is not `AWSPENDING`. `unknown_step`: Secrets Manager asked for a step the function does not know. |
| `error.type`                                  | Every event | `RotationStateError`.                                                                                                                                                                                                                                     |
| `error.message`                               | Every event | What is wrong, in words.                                                                                                                                                                                                                                  |

## Consuming the logs

### What CloudTrail already records

CloudTrail records each Secrets Manager API call as a management event, with
the caller, time, source address and outcome: `RotateSecret`, `PutSecretValue`,
`UpdateSecretVersionStage`, `GetSecretValue` and `DeleteSecret`. It does not
record which keys a rotation added or retired, whether the pending version passed
validation, or why a step failed. The function's log records that.

To find who started a manual rotation, look up `RotateSecret` in CloudTrail for
the secret's ARN. To join a rotation's log events to the calls that made its
version, use `aws.secretsmanager.secret.arn` and `aws.secretsmanager.secret.version.id`
(or `event.id`) against the version ID in the request parameters of the
`PutSecretValue` and `UpdateSecretVersionStage` events.

CloudTrail's 90-day event history is not an audit trail. Make sure a trail is
enabled and retained for as long as you need it.

### Query the log group

In CloudWatch Logs Insights, fields with dots in their names need backticks. To list
every key change:

```
fields @timestamp, `event.id`, `jwks.kids.added`, `jwks.kids.removed`
| filter `event.action` = "finish_secret"
| sort @timestamp desc
```

To list failures:

```
fields @timestamp, `event.action`, `event.reason`, `error.type`, `error.message`, `event.id`
| filter `event.outcome` = "failure"
| sort @timestamp desc
```

### Alarm on a failed rotation

The construct creates no alarm, because it cannot choose where to send it.
Secrets Manager retries a failed step, so a single failure usually logs
several records. This example counts the failures and alarms on the first:

```ts
import { Duration } from 'aws-cdk-lib';
import { Alarm, ComparisonOperator, TreatMissingData } from 'aws-cdk-lib/aws-cloudwatch';
import { FilterPattern } from 'aws-cdk-lib/aws-logs';

const failures = jwksSecret.rotationLogGroup.addMetricFilter('RotationFailures', {
  metricNamespace: 'JwksSecret',
  metricName: 'RotationFailures',
  filterPattern: FilterPattern.literal('{ $.[\'event.outcome\'] = "failure" }'),
  metricValue: '1',
});

new Alarm(this, 'RotationFailed', {
  metric: failures.metric({ statistic: 'Sum', period: Duration.minutes(5) }),
  threshold: 1,
  evaluationPeriods: 1,
  comparisonOperator: ComparisonOperator.GREATER_THAN_OR_EQUAL_TO_THRESHOLD,
  treatMissingData: TreatMissingData.NOT_BREACHING,
});
```

Add an alarm action, such as an SNS topic, with `alarm.addAlarmAction(...)`.
The function only runs when a rotation happens, every 28 days by default, so a
quiet log group is normal and is not a sign that logging has stopped.
